Состояние: 2026-09-11, Content `a5c137c693`, RobustToolbox `f10a3a6af`.
Исследованы исходники и документация. Игра, сборка, тесты и рендерер не запускались.
API инструмента ниже — предложение, таких mapping endpoints сейчас в проекте нет.

**Текущий рабочий процесс**

`mapping [MapId] [path] [isGrid]` создаёт карту без MapInit либо загружает сохранение. Номер должен быть свободен. Явное `true` в третьем аргументе означает Grid, `false` — Map. Без аргумента команда сначала пробует Map, затем Grid; при загрузке грида это может дать лишнюю ошибку в логе. Загрузка сохраняет YAML UID через `StoreYamlUids = true`.

Примеры для файлов текущего репозитория:

```text
mapping 100 "Maps/_Exodus/Outpost/colossus_central.yml" false
mapping 101 "Maps/_Exodus/Supercapitals/chengdu.yml" true
```

Это два независимых примера. После загрузки команда переводит игрока в aghost при необходимости, телепортирует его на карту, включает autosave и клиентские инструменты. Также глобально отключает события и автоматический вызов шаттла. Поэтому для автоматизации лучше обращаться к системам загрузки напрямую в отдельном сервере для разработки.

Клиентский setup показывает маркеры и подполье, отключает освещение и загружает mapping actions. Ручная работа включает F5/F6, размещение линий и прямоугольников, поворот, VV, декали, доступы и связи устройств. Копирование прототипа клавишей P не переносит индивидуальные настройки выбранной сущности. Порядок работы также описан в [официальном руководстве](https://docs.spacestation14.com/en/space-station-14/mapping/guides/general-guide.html).

Локальные источники: [MappingCommand](../../../Content.Server/Mapping/MappingCommand.cs), [клиентский setup](../../../Content.Client/Commands/MappingClientSideSetupCommand.cs), [MappingTests](../../../Content.IntegrationTests/Tests/Mapping/MappingTests.cs).

**Map, Grid и сохранение**

| Команда | Область сохранения | Особенность |
| --- | --- | --- |
| `savegrid <grid NetEntity> <path>` | Один грид и его дочерние сущности | Нет запрета на сохранение после MapInit |
| `savemap <MapId> <path> [force]` | Карта, её гриды и дочерние сущности | После MapInit требует `true` |

Выбор определяется структурой файла, а не размером станции. У `colossus_central.yml` сейчас `meta.category: Map`, один map и один grid. У `chengdu.yml` — `Grid`. Даже единственный грид может нуждаться в сохранении вместе с компонентами карты.

MapId, runtime EntityUid, сетевой NetEntity и UID внутри YAML — разные идентификаторы. Номер `100` из `mapping` нельзя автоматически передавать в `savegrid` как ID грида. Для просмотра есть `lsmap`, `lsgrid`, F3/VV; при передаче ID нужно учитывать, какой именно вид принимает команда.

Сохранение идёт в серверный UserData, обычно `bin/Content.Server/data`, а не непосредственно в `Resources/Maps`. Загрузчик сначала ищет UserData и затем ресурсы. Одинаковый относительный путь может загрузить старую рабочую копию вместо файла репозитория; об этом выводится warning. Будущая тулза должна возвращать фактический источник и хеш загруженного файла.

Autosave включён по умолчанию: 600 секунд, `Autosaves/<name>/<timestamp>-AUTO.yml`. На очередной проверке объект после MapInit исключается из автосохранения. Это резервная копия, а не история отката каждого действия.

Источники: [команды загрузки и сохранения](../../../RobustToolbox/Robust.Server/Console/Commands/MapCommands.cs), [чтение и запись файлов](../../../RobustToolbox/Robust.Shared/EntitySerialization/Systems/MapLoaderSystem.cs), [MappingSystem](../../../Content.Server/Mapping/MappingSystem.cs), [CVars](../../../Content.Shared/CCVar/CCVars.Mapping.cs), [карта Колосса](../../../Resources/Maps/_Exodus/Outpost/colossus_central.yml), [грид Chengdu](../../../Resources/Maps/_Exodus/Supercapitals/chengdu.yml).

**MapInit и цикл тестирования**

`mapinit <MapId>` меняет lifecycle сущностей, вызывает обработчики MapInit и снимает паузу карты. Спавнеры могут породить содержимое и удалить себя, helpers применяют настройки, системы начинают симуляцию. Повторный вызов запрещён. Обычная пауза не восстанавливает исходные сущности.

Post-init состояние сериализуется и восстанавливается при загрузке. Поэтому `mapping` не превращает сохранённую игровую копию обратно в исходник. Удаление `mapInit: true` из YAML тоже не вернёт потраченные спавнеры и первоначальные данные. `SerializationOptions.ExpectPreInit` лишь пишет ошибку в лог; для экспортера нужна отдельная строгая проверка всего экспортируемого набора сущностей.

Тестировать удобнее сохранённую копию, оставляя рабочую карту 100 до MapInit. Если 101 свободен, для Map:

```text
savemap 100 "Mapping/checkpoint-map.yml"
loadmap 101 "Mapping/checkpoint-map.yml" 0 0 0 true
mapinit 101
tp 0 0 101
```

Для Grid вместо первых двух строк:

```text
savegrid <grid NetEntity> "Mapping/checkpoint-grid.yml"
loadgrid 101 "Mapping/checkpoint-grid.yml" 0 0 0 true
```

Последний `true` у загрузки сохраняет YAML UID. При повторении нужен свободный MapId. Перед удалением тестовой карты необходимо вернуться на рабочую. Если `loadgrid` получает уже инициализированную карту, загруженные сущности инициализируются сразу. Нулевой поворот в примерах намеренный: текущий `loadgrid` принимает градусы, а `loadmap` создаёт `Angle` из радиан.

Отдельная карта в одном процессе удобна для ручного теста, но общие CVars и системы остаются общими. Для воспроизводимого автоматического тестирования предпочтителен отдельный процесс.

Нужны два уровня теста: локальная симуляция после MapInit и обычная загрузка станции/корабля своим игровым сценарием. Голый `loadmap + mapinit` не выполняет весь путь `GameMapPrototype`, `PostGameMapLoad` и настройки StationSystem. У Колосса это особенно заметно: роли, компоненты станции и дополнительные компоненты грида описаны в gameMap `Frontier` отдельно от YAML карты.

Источники: [InitializeMap](../../../RobustToolbox/Robust.Shared/GameObjects/Systems/SharedMapSystem.MapInit.cs), [опции](../../../RobustToolbox/Robust.Shared/EntitySerialization/Options.cs), [сериализатор](../../../RobustToolbox/Robust.Shared/EntitySerialization/EntitySerializer.cs), [десериализатор](../../../RobustToolbox/Robust.Shared/EntitySerialization/EntityDeserializer.cs), [загрузка в существующую карту](../../../RobustToolbox/Robust.Shared/EntitySerialization/Systems/MapLoaderSystem.LoadMap.cs), [gameMap Колосса](../../../Resources/Prototypes/_Mono/Outpost/caelestinus.yml), [StationSystem](../../../Content.Server/Station/Systems/StationSystem.cs).

**Массовая окраска труб**

```text
colornetwork <NetEntity обычной трубы> Pipe #0055cc
```

Команда красит связанную NodeGroup выбранной трубы. `Pipe` регистрозависим; это имя категории, а не слой трубы. Стандартные цвета из настроек spray painter:

| Назначение | Цвет |
| --- | --- |
| Раздача / distro | `#0055cc` |
| Отходы / waste | `#990000` |
| Воздух / air | `#03fcd3` |
| Смесь / mix | `#947507` |

Начальную сущность следует выбирать среди обычных труб: команда обращается к `Nodes["pipe"]`, а у насоса или другого устройства имена портов могут отличаться. При ещё не построенной NodeGroup ничего не произойдёт. По коду пересборка сетей работает до MapInit, поэтому после прокладки достаточно обработки очереди узлов сервером; инициализировать карту ради окраски не требуется. Это вывод из исходников, без проверки в запущенной игре.

Цвет не разделяет сети. Соединение определяется гридом, закреплением, соседством, направлениями и слоем. Слои здесь — Primary/Secondary/Tertiary; для команды во всех случаях остаётся `Pipe`. При массовом размещении линией/прямоугольником клиентский выбор слоя по положению курсора отключён, поэтому агенту слой лучше задавать явно.

`nodevis` позволяет проверить сети. `nodevisfilter Pipe` переключает видимость категории, а не означает «показать только трубы».

Для нового API цвет нужно менять через `AtmosPipeColorSystem.SetColor`, слой — через `AtmosPipeLayersSystem.SetPipeLayer`. При `user: null` последний не выполняет пользовательскую проверку перекрытий: это должен проверить инструмент. Для окраски сеть следует выбирать парой entity + node name и сверять границы операции. Disposals требуют собственного адаптера: их соединения не являются обычной Pipe NodeGroup.

Источники: [ColorNetworkCommand](../../../Content.Server/Sandbox/Commands/ColorNetworkCommand.cs), [цвета](../../../Resources/Prototypes/Entities/Objects/Tools/spray_painter.yml), [PipeNode](../../../Content.Server/NodeContainer/Nodes/PipeNode.cs), [NodeGroupSystem](../../../Content.Server/NodeContainer/EntitySystems/NodeGroupSystem.cs), [выбор слоя при размещении](../../../Content.Client/Atmos/AlignAtmosPipeLayers.cs), [API цвета](../../../Content.Server/Atmos/Piping/EntitySystems/AtmosPipeColorSystem.cs), [API слоя](../../../Content.Server/Atmos/EntitySystems/AtmosPipeLayersSystem.cs).

**Предлагаемое устройство инструмента**

Агент формирует план и вызывает структурированные операции. Исполнитель внутри отдельного Robust-сервера применяет их через системы проекта, возвращает состав участка, изображения и диагностику. Рабочее состояние всегда остаётся до MapInit; тестовые копии одноразовые.

```mermaid
flowchart LR
    P[Промпт и ограничения] --> A[Агент]
    A --> T[CLI или MCP]
    T --> E[Исполнитель Exodus]
    E --> D[Рабочая карта до MapInit]
    D --> C[Сохранённая ревизия]
    C --> R[Тестовый процесс и MapInit]
    R --> F[Диагностика и изображения]
    F --> A
    C --> X[Экспорт Map или Grid]
```

Внешний адаптер можно разместить в `Tools/_Exodus/Mapping`, серверную логику — в `Content.Server/_Exodus/Mapping`. Состояние ECS-сессии хранится на отдельной служебной сущности, исключённой из экспорта; журнал ревизий и файлы может хранить внешний процесс. Для транспорта уже есть аналог `IStatusHost` в Exodus WebAPI. Вызовы ECS выполняются на основном потоке, а ответ об успехе отправляется после завершения операции. Образец ожидания есть в `ServerApi.Utility.RunOnMainThread`; методы private, это паттерн для реализации, а не готовый публичный API.

Интерфейс ограничивается рабочей сессией и её файлами, включается для локального сервера разработки. Агенту не требуется произвольное исполнение C# или консольных строк. Планирование и поиск маршрутов можно выполнять над снимком данных вне игрового потока; применение требует повторной проверки ревизии.

Возможный контракт; названия ниже предложены для разработки:

| Операция | Результат |
| --- | --- |
| `open/create` | Сессия, категория Map/Grid, гриды, источник, хеш, lifecycle, ревизия |
| `catalog.search/describe` | Существующие прототипы, разрешённые поля, sprites, размеры и порты, если они описаны данными/адаптером |
| `inspect` | Тайлы, сущности, overrides, декали, контейнеры и связи указанного участка |
| `render` | Обзор или участок с координатами, режимом и номером ревизии |
| `apply_batch` | Пакет размещения, удаления, тайлов, поворотов, настроек и связей; diff и новая ревизия |
| `checkpoint/restore` | Сохранённый исходник и восстановление рабочей сессии |
| `validate` | Ошибки структуры и геометрии с координатами и проверенными условиями |
| `test` | Инициализация отдельной копии, наблюдения за симуляцией и логами |
| `export` | Проверенный pre-init Map/Grid и отчёт об изменениях |

Каждый изменяющий запрос несёт session, expectedRevision и operationId. Повтор запроса не должен дублировать сущности, а изменение человеком после inspect должно приводить к конфликту ревизии. Ссылки агента — handles сессии, сопоставленные YAML UID и текущим runtime UID. После reload runtime UID меняются; старые handles необходимо перепривязать или явно инвалидировать. Координаты задаются относительно конкретного грида; единицы поворота у API едины и явны.

Агенту нужен компактный контекст: обзор всей карты, затем выбранный участок и соседние помещения; категории объектов, занятые клетки, проходы, порты и сети. Передача десятков тысяч сущностей в каждый запрос не нужна. Изображение дополняет структуру: по картинке нельзя надёжно проверить доступы, содержимое контейнеров или связь кнопки с дверью.

Модель выбирает намерение, а исполнитель обеспечивает допустимые операции. Для «проложи воздух к медблоку» последующий инженерный модуль должен найти входной порт, маршрут и фитинги, явно выбрать слой, проверить пересечения и конечную сеть, затем покрасить её. Простая смена цвета не является проверкой соединения. Правила помещений, стили и каталоги prefab лучше хранить в YAML `_Exodus`, а сложную геометрию и проверки — в общих адаптерах систем.

**Что переиспользовать и что придётся разработать**

| Основа проекта | Применение и предел |
| --- | --- |
| `MapLoaderSystem` / `EntitySerializer` | Штатная загрузка и экспорт, UID, references, tilemap. `ExpectPreInit` не заменяет запрет экспорта игрового состояния |
| `SharedMapSystem.SetTiles`, transform/anchor systems | Пакетное изменение тайлов и корректное размещение объектов |
| Atmos, Decal, DeviceLink systems | Изменения с нужными событиями и обновлением состояния |
| Exodus WebAPI / ServerApi.Utility | Образцы HTTP и ожидания результата основного потока; готовых mapping endpoints нет |
| `Content.MapRenderer` | Готовый экспорт изображения; сейчас запускает игровую копию, нужен отдельный pre-init режим |
| `DungeonRoomPrototype`, `DungeonSystem.SpawnRoom` | Атлас, геометрия комнат и декали; SpawnRoom создаёт сущности по прототипу и теряет индивидуальные overrides/контейнеры/связи |
| `merge_grids` | Перенос тайлов и дочерних сущностей; не гарантирует перенос grid components и декалей |
| Procedural auto-cabling | Пример поиска маршрутов LV; универсальную разводку инженерных сетей не предоставляет |

Рендерер композитит тайлы, декали и спрайты, а не полный игровой GPU viewport. Он не доказывает корректность освещения и визуальных эффектов. Для них нужен клиент тестовой копии. Экспортироваться должен исходник соответствующей ревизии, а не состояние после рендера/симуляции.

Большая часть карты — не список «прототип + x/y»: есть бинарные тайлы в Base64, локальные UID, родительские связи, component overrides, контейнеры, nullspace references и настройки карты. Для MVP авторитетный экспорт лучше поручить Robust. Прямое редактирование YAML допустимо для контролируемых операций, но потребует собственного корректного round-trip и учёта формата.

Универсальный region copy должен переносить overrides, контейнеры, ссылки и декали. Внутренние ссылки перепривязываются к копиям, внешние требуют явной политики. Поэтому полноценный prefab clone стоит делать отдельным этапом; SpawnRoom и merge_grids не считать его готовой реализацией.

**Откат, проверка и производительность**

Для первого этапа достаточно checkpoint всей рабочей карты перед логическим пакетом, предварительной проверки пакета и восстановления checkpoint при ошибке. Это восстановление документа; произвольные побочные эффекты ECS не являются обратимой транзакцией. Если действие затрагивает состояние вне документа, надёжное восстановление требует пересоздания рабочего процесса. Запись checkpoint/export должна идти во временный файл с заменой после успешной сериализации: существующий path overload загрузчика открывает файл на запись до завершения сериализации.

Проверки следует разделить на явно названные результаты:

- Структура: загрузка штатным загрузчиком, существование прототипов, корректность references, category, отсутствие post-init сущностей, сохранение UID и семантики после повторной загрузки.
- Геометрия: размещение на нужном гриде, дубли, закрепление, проходимость между заданными точками, требуемые свободные клетки дверей/шлюзов.
- Инженерия: порты и связность сетей, случайное соединение distro/waste, питание конкретных обязательных потребителей, ожидаемые герметичные зоны и доступы. Эти проверки требуют правил из задания, чтобы космический шлюз не считался ошибочной разгерметизацией.
- Симуляция: тестовая копия после MapInit и нужного сценария загрузки, наблюдение за давлением/температурой/питанием, ошибки серверных логов. В отчёте должны быть длительность, начальные условия и непроверенные требования.

Имеющиеся `MappingTests`, `SaveLoadMapTest`, `PostMapInitTest` полезны как образцы. Они не подтверждают работоспособность каждой комнаты. `StationPowerTests` — Explicit и со списком конкретных станций, его нельзя выдавать за проверку любого Exodus-корабля. Новому инструменту понадобятся проверки его контракта: неуспешный batch, повтор operationId, устаревшая revision, ссылки при копировании, запрет post-init экспорта, воспроизводимое восстановление.

Работа с сущностями ограничивается целевой картой/гридом/участком, сетевой обход — выбранной сетью. Обычный EntityQueryEnumerator исключает paused entities, поэтому для инспекции маппинга нужен осознанный запрос с учётом паузы и ограничения области. Постоянного сканирования всех игровых сущностей быть не должно. Для больших карт нужны ограниченные пакеты, ожидание пересборки сетей и deferred operations, а затем coherent snapshot для render/save. Сохранение большого checkpoint само по себе может быть дорогим; это измеряется в отдельном сервере разработки.

Качество карт для 80+ игроков и 80+ гридов оценивается отдельным нагрузочным сценарием. Успешный короткий тест одного помещения не доказывает серверную производительность. Полезные метрики инструмента: время загрузки/сохранения, время пакета, время пересборки сетей, количество сущностей и время тика в тесте.

Источники тестов: [MappingTests](../../../Content.IntegrationTests/Tests/Mapping/MappingTests.cs), [SaveLoadMapTest](../../../Content.IntegrationTests/Tests/SaveLoadMapTest.cs), [PostMapInitTest](../../../Content.IntegrationTests/Tests/PostMapInitTest.cs), [StationPowerTests](../../../Content.IntegrationTests/Tests/Power/StationPowerTests.cs).

**Порядок реализации**

1. Вертикальный прототип: открыть существующий pre-init Map/Grid, inspect участка, разместить пол/стены/дверь/свет, checkpoint, сохранить и повторно загрузить, получить изображение. Затем отдельная тестовая копия с MapInit. Критерий: рабочий исходник остался pre-init, изменения соответствуют diff, повторный запрос не дублирует объекты, восстановление возвращает предыдущую ревизию.
2. Каталог реальных прототипов, удобные региональные запросы, координатные изображения, доступы/связи устройств, согласование ручных правок с revision.
3. Полноценные prefab со ссылками и контейнерами, инженерные адаптеры для питания/атмоса/disposals, настройка стилей и требований в YAML.
4. Генерация крупных планировок с графом помещений, ограничениями связности и итерациями по визуальному и техническому отчёту. Для Колосса — изменения выбранных участков с сохранением окружения.

Первый демонстрационный промпт: «На выбранном участке сделай герметичную кладовую 6×8, вход с юга, два стеллажа и освещение; соседние помещения сохрани». Размер следует заранее трактовать как внутренний или внешний в design spec. Автоматическое подключение питания и атмоса добавляется после базового цикла inspect → batch → save → reload → test.
