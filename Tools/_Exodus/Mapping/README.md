# Mapping toolkit для ИИ-агентов

Инструмент создаёт и редактирует SS14-карты **до MapInit** через JSON-операции, сохраняет сессии и экспортирует обычный YAML формата 7. ИИ переводит задачу в рецепт или пакет операций; сам инструмент не содержит LLM и не принимает свободный текст как команду маппинга.

Состояние редактора хранится в отдельном JSON-файле. `MapInit` запускается только над тестовой копией в `engine-check`. Источник остаётся доступен для дальнейших правок.

## Установка и запуск

Команды ниже выполняются из корня репозитория в PowerShell. Нужен Python с установленными зависимостями:

```powershell
py -3 -m pip install -r Tools/_Exodus/Mapping/requirements.txt
py -3 Tools/_Exodus/Mapping/mapping.py --help

$mappingTool = "Tools/_Exodus/Mapping/mapping.py"
$mappingSession = "tmp/mapping/capsule.session.json"
```

Рабочие команды возвращают JSON в stdout; обработанные ошибки — объект с `error` и `type`. Код выхода `1` означает ошибку или результат проверки `passed: false`. Справка `--help` и ошибки аргументов используют обычный формат argparse. Агент должен разбирать JSON и проверять код выхода, а не искать фразу об успехе в тексте.

Пути сессий, временных экспортов и отчётов выбирайте вне `Resources`. Не добавляйте их в коммит. `--resources PATH` — общий аргумент **перед** подкомандой; по умолчанию используется `Resources` этого репозитория.

## Быстрый пример: спасательная капсула

Готовый [рецепт](examples/rescue_capsule.json) задаёт грид 6×6, размещение оборудования, начальную атмосферу и требования для проверок. Его YAML-результат находится в [Resources/Maps/_Exodus/Shuttles/rescue_capsule.yml](../../../Resources/Maps/_Exodus/Shuttles/rescue_capsule.yml). [Описание капсулы и выполненные проверки](examples/rescue_capsule.md) включают воспроизводимый сценарий с двумя пассажирами. Для повторного создания используйте новую сессию и новый путь вывода:

```powershell
py -3 $mappingTool recipe Tools/_Exodus/Mapping/examples/rescue_capsule.json --session $mappingSession --output tmp/mapping/rescue_capsule.yml
py -3 $mappingTool validate --session $mappingSession
py -3 $mappingTool render --session $mappingSession --output tmp/mapping/capsule.svg
py -3 $mappingTool render --session $mappingSession --output tmp/mapping/capsule.png
```

`recipe` сохраняет `requirements` внутри сессии. Повторный `recipe` с уже существующей сессией отклоняется; для продолжения работы используйте `inspect` и `apply`. Экспорт нового рецепта поверх существующего файла карты также отклоняется: откройте существующую карту для правок или выберите новый путь для результата.

Создание пустой карты и открытие существующей — отдельные команды:

```powershell
py -3 $mappingTool create --session tmp/mapping/new-grid.session.json --category Grid --name "Новый шаттл"
py -3 $mappingTool create --session tmp/mapping/new-map.session.json --category Map --name "Новая карта"
py -3 $mappingTool open Resources/Maps/_Exodus/Shuttles/rescue_capsule.yml --session tmp/mapping/existing-capsule.session.json
```

Новый `Grid` содержит один грид с YAML UID `1`. Новый `Map` содержит карту с UID `1` и грид с UID `2`. Физика шаттла, гравитация, атмосфера и оборудование задаются явно в рецепте/операциях. Пустой грид сам по себе не становится готовым кораблём.

## Каталог и осмотр

```powershell
py -3 $mappingTool catalog "GasPipeStraight" --limit 10
py -3 $mappingTool catalog "FloorShuttle" --kind tile
py -3 $mappingTool catalog --id AirlockShuttle
py -3 $mappingTool inspect --session $mappingSession --grid 1 --bounds 0 0 5 5
```

Поиск учитывает ID, YAML-имя и путь файла прототипа. `catalog --id` возвращает происхождение, родителей, признак `abstract`, разрешённые YAML-данные в `data` и текст `yaml`, сохраняющий `!type:`/`!enum:`-теги. Обычный JSON `data` не передаёт атрибуты этих тегов.

Наследование учитывает порядок родителей: ребёнок имеет приоритет, затем первый родитель. Компоненты объединяются по типу; обычные поля компонентов, включая списки и словари, заменяются целиком. Прямые поля `AlwaysPushInheritance`/`NeverPushInheritance` определяются по доступным C#-исходникам. Это представление авторского YAML: C# defaults, локализация, runtime hooks и полная семантика произвольных вложенных сериализаторов не вычисляются.

В инструменте `grid` и `uid` — **ID из YAML**, не серверный `MapId`, `EntityUid` или `NetEntity`. Координаты локальны относительно грида; центр тайла `(x, y)` обычно находится в `(x + 0.5, y + 0.5)`. `bounds: [x0, y0, x1, y1]` включают обе крайние клетки. Повороты операций задаются в градусах. Если документ содержит несколько гридов, для операций и `inspect` укажите `grid` явно.

## Пакеты правок и повторные запросы

Сначала получите текущую ревизию и при необходимости сделайте checkpoint:

```powershell
py -3 $mappingTool checkpoint --session $mappingSession --name before-helm-edit
$mappingRevision = (py -3 $mappingTool inspect --session $mappingSession --grid 1 | ConvertFrom-Json).revision
```

Пример `tmp/mapping/edit.json` для сессии, созданной из рецепта капсулы:

```json
{
  "operation_id": "capsule/helm-label/001",
  "operations": [
    {
      "op": "patch",
      "entity": "helm",
      "components": [
        { "type": "MetaData", "name": "Штурвал спасательной капсулы" }
      ]
    }
  ]
}
```

```powershell
py -3 $mappingTool apply --session $mappingSession --batch tmp/mapping/edit.json --expected-revision $mappingRevision
```

`expected_revision` и `operation_id` обязательны. Их можно передать полями JSON-пакета либо аргументами `--expected-revision` и `--operation-id`; аргументы имеют приоритет. Допустим и JSON-массив операций, если оба значения переданы аргументами.

Пакет применяется целиком на копии документа и сохраняется только после структурной проверки. Несовпадение ревизии отклоняет новый пакет. Повтор того же `operation_id` с теми же операциями возвращает сохранённую квитанцию с `replayed: true`, не создавая дубликаты; при повторе текущую ревизию смотрите в `current_revision`. Тот же ID с другим содержимым отклоняется. Для новой правки используйте новый `operation_id`.

Поддерживаемые операции:

| `op` | Основные поля | Действие |
| --- | --- | --- |
| `tiles` | `grid`, `bounds`, `tile`; необязательно `flags`, `variant`, `rotationMirroring` | Заполняет прямоугольник тайлов; `Space` очищает тайлы. |
| `spawn` | `prototype`, `x`, `y`; необязательно `grid`, `rotation`, `anchored`, `key`, `components` | Создаёт сущность и при наличии `key` регистрирует логическое имя в сессии. |
| `patch` | `entity`, `components` | Добавляет компоненты или заменяет перечисленные поля; неперечисленные поля сохраняет. |
| `move` | `entity`; необязательно `x`, `y`, `rotation`, `grid` | Меняет положение, поворот или родительский грид. |
| `delete` | `entity` | Удаляет сущность без дочерних объектов; удаление корней map/grid не поддерживается. |

`entity` принимает числовой YAML UID или ранее созданный `key`. Логические имена живут в сессии: после `open` экспортированного YAML используйте UID из `inspect`. Внутри данных компонента ссылка задаётся как `{"$entity": "helm"}`, а YAML-тег — как `{"$tag": "!type:SomeType", "$value": {...}}`. Ссылаться можно на уже существующую сущность или на результат предыдущей операции этого пакета.

Списки и словари в `patch` заменяются **полностью** на уровне указанного поля. Например, передавая `DeviceList.devices`, нужно перечислить весь нужный список. Массовое изменение — пакет из нескольких `patch`; автоматического поиска маршрута труб или проверки их соединений сейчас нет.

## Checkpoint, восстановление и экспорт

```powershell
$mappingRevision = (py -3 $mappingTool inspect --session $mappingSession --grid 1 | ConvertFrom-Json).revision
py -3 $mappingTool restore --session $mappingSession --name before-helm-edit --expected-revision $mappingRevision
py -3 $mappingTool export --session $mappingSession --output tmp/mapping/rescue_capsule.yml
```

Имена checkpoint уникальны в пределах сессии. Восстановление требует текущую ревизию и возвращает документ, логические имена и квитанции операций к сохранённому состоянию. Файлы, экспортированные ранее, от `restore` не меняются: результат нужно экспортировать отдельно.

Экспорт проверяет SHA-256 назначения. Он разрешён в новый файл либо в файл, который сессия открыла/ранее экспортировала и который после этого не меняли снаружи. Чужие изменения вызывают конфликт; выбирайте новый путь или открывайте актуальную карту в новой сессии.

Перед записью карта и квитанция экспорта связываются журналом `pendingExports`. Если процесс прервался между записью YAML и обновлением сессии, повторите тот же `export` с той же сессией и назначением: он принимает только прежний файл либо точный уже подготовленный результат. Не очищайте `pendingExports` вручную. Сессия защищена `.lock` от одновременных записей; оставшийся после аварии lock удаляют только после завершения использовавшего его процесса.

Редактор сохраняет неизвестные поля и YAML-теги, но переписывает форматирование и комментарии исходного YAML. Пост-MapInit документы отклоняются при открытии и экспорте. Удаление `mapInit` вручную не восстанавливает уничтоженные спавнеры и остальные исходные данные.

## Preview и проверки

`render`/`render-file` создают самостоятельный SVG или PNG с координатами, легендой и условными обозначениями. Малые гриды отображаются крупно; оборудование отмечено короткими подписями (`HELM`, `SEAT`, `GEN` и другими), расшифрованными в легенде. Кабели и трубы рисуются под корпусом и оборудованием. SVG содержит подсказки с прототипом, UID, положением и слоем сущности. Каждый грид рисуется отдельной панелью в своих координатах; `--grid` и `--bounds` ограничивают область. PNG использует Pillow.

Это схема размещения, а не игровой скриншот. Она не воспроизводит RSI-слои, освещение и runtime-связи. Содержимое контейнеров может находиться в тех же координатах, что и контейнер.

```powershell
py -3 $mappingTool render-file Resources/Maps/_Exodus/Shuttles/rescue_capsule.yml --output tmp/mapping/current.svg
py -3 $mappingTool validate-file Resources/Maps/_Exodus/Shuttles/rescue_capsule.yml --requirements Tools/_Exodus/Mapping/examples/rescue_capsule.json
```

`validate` проверяет сессию, `validate-file` — YAML. `--requirements` принимает объект требований либо целый recipe с полем `requirements`. Для сессии без этого аргумента используются требования, сохранённые при `recipe`.

Поддерживаются `required_prototypes` (минимальное количество каждого прототипа во всём документе), `max_size` (максимальная ширина/высота каждого грида по тайлам) и `breathable_tiles` (локальные клетки каждого грида, где проверяется записанная начальная газовая смесь). Проверяются также формат карты, ID/Transform-иерархия, чанки и наличие прототипов; повторные размещения и некоторые закреплённые объекты без тайла выводятся как предупреждения.

`passed: true` у этой проверки означает соответствие проверкам чертежа. В ответе `not_checked` перечислены ограничения, включая C#-схемы полей, работу электросети, герметичность корпуса и управление кораблём.

## Проверка существующим сервером

`engine-check` запускает уже собранный `bin/Content.Server/Content.Server.dll` через `dotnet`. Команда **не делает build**. Бинарник и его зависимости должны соответствовать текущим ресурсам. Каждый запуск получает отдельные настройки, UserData и loopback-порт; для отчёта нужен новый каталог.

```powershell
py -3 $mappingTool engine-check tmp/mapping/rescue_capsule.yml --output tmp/mapping/engine-capsule-001 --seconds 10 --timeout 180 --requirements Tools/_Exodus/Mapping/examples/rescue_capsule.json
```

Проверка выполняет два отдельных запуска сервера:

1. **Authoring:** загружает исходник без MapInit, сохраняет его штатным сериализатором и проверяет, что карта осталась неинициализированной. Канонический pre-init результат: `authoring/data/blueprint.yml`.
2. **Simulation:** повторно загружает копию результата в другом процессе, проверяет количество гридов, выполняет `mapinit`, ждёт заданное время и сохраняет диагностический `simulation/data/simulation.yml`.

Корневой `report.json` и серверные логи содержат результаты и ошибки. При указанных требованиях `simulation_checks.grids[].air_checks` содержит замеры воздуха по нужным клеткам. `simulation_checks.power_telemetry` читается из сохранённого `PowerNetworkBattery`; эти значения не доказывают, что запитан каждый потребитель. Исходный файл не подменяется канонической или симуляционной копией.

Проверка загрузки и наблюдение за симуляцией не выполняют ввод игрока, пилотирование или нагрузочный тест на 80 игроков/гридов. Не используйте `simulation.yml` как источник для дальнейшего маппинга: это пост-MapInit снимок.

Для ручной проверки экспортированного грида можно загрузить его в редакторе командой `mapping 100 "<путь-к-YAML>" true`, предварительно поместив файл в доступный серверу Resources/UserData. Для Map-файла третий аргумент — `false`. До ручного `mapinit` сохраняйте исходник или тестируйте отдельную копию. ID в игровых командах и в JSON-сессии различаются.

## Тесты и границы реализации

```powershell
py -3 -m unittest discover -s Tools/_Exodus/Mapping/tests -v
```

Это Python-тесты кодека, операций, каталога, preview и сессий; сборка игры не запускается. Поддерживается редактирование pre-init документов формата 7, создание `Grid`/`Map`, перечисленные JSON-операции и диагностика существующим сервером. Сейчас нет готового MCP-сервера, подключения к живому редактору, автоматической прокладки инженерных сетей, генерации планировки из текста внутри инструмента и автоматического undo для произвольных действий игровых систем.
